# BLACKOUT 4.0 — етап 1: аудит і план міграції

Контрольна точка перед 4.0: гілка `baseline/blackout-3.4-premium` (= `design/premium-black` @ 3cead3d).
Робоча гілка: `design/blackout-4.0`. `main` не змінюється.

## 1. Архітектура зараз

- Один файл `index.html` (≈1,5 МБ), збирається скриптом із базового коду 3.3 + модулі:
  - `pb` — дизайн Living Energy, головна схема, BT-доповнення (Fossibot, Bluetti, авто-підключення, watchdog, керування виходами);
  - `sv` — графіки відключень svitlo.live;
  - `ef` — EcoFlow (шифрований протокол);
  - `tesla` — Tesla BLE;
  - `ui2` — підвкладки Bluetooth, живий % станції;
  - `car3d` — 3D-модель авто (WebGL) + упакована модель.
- Стан користувача: `localStorage['blackout_v1']` (об'єкт `S`). Оновлення APK зберігають дані (фіксований підпис, зростаючий versionCode).
- Рендер: `render()` повністю перебудовує `#app` через innerHTML для поточної вкладки. Живі цифри оновлюються точково (btUi, pbRefresh, tsUi), але перехід вкладок і багато дій = повний перерендер.
- Модулі розширюють один одного обгортками (`render`, `btConnect`, `btFrame2`, `vBt`, `pbMetrics`…). Порядок обгорток важливий.
- Пристрої пишуть стан у глобальні об'єкти `BT`, `BLUP`, `EF`, `TS`; UI читає їх напряму.

## 2. Інвентар функцій (що не можна втратити)

| Блок | Що є | Статус |

| Станції | записи заряд/розряд, Вт·год, вартість з мережі, каталог моделей, сервіс-центри | працює |
| Fossibot F2400 BLE | заряд, вхід/вихід, мережа В/Гц, час до повного/розряду; керування AC/DC/USB/LED | перевірено на пристрої |
| Bluetti AC2P BLE | заряд, вхід/вихід | перевірено на пристрої |
| EcoFlow BLE | шифрований вхід, протобуф-дані | лише на імітації |

| Інше | нагадування (local notifications), keep-awake, темна/світла тема, режим анімацій, тріал-блокування | працює |
| Віджет на робочому столі | тільки макет | не реалізовано |

Чого **немає** в коді (на референсі є — не вигадуємо, поки не реалізуємо по-справжньому):
- автоматизації «Режим економії / Нічна зарядка / Живлення дому» — станції не дають таких команд, можливі лише як правила застосунку поверх керування виходами Fossibot;
- історії потужності в часі — телеметрія зараз не записується, тому для «Аналітики» потрібен новий журнал (кільцевий буфер у сховищі);
- температури — жоден підключений протокол її поки не віддає (у Fossibot регістр не підтверджено);
- сонячних панелей — у вашій системі немає, показуємо лише якщо з'являться в даних.

## 3. Ризики редизайну

1. Повний перерендер через innerHTML → ривки й скидання прокрутки. Для нового «Огляду» — точкові оновлення.
2. Ланцюжок обгорток: нова навігація не має ламати порядок `render`-обгорток (BT-картки, акордеони, підвкладки).
3. Збірка через заміну рядків: кожна заміна перевіряється (assert), але нові зміни базового коду ламають заміни — нові екрани робимо окремими модулями.
4. Зображення обладнання: реальні фото/рендери брендів — чужі матеріали. Потрібні зображення, які ви маєте право використовувати (прес-кіт виробника / дозвіл). До того — нейтральні умовні.
5. Розмір: 3D-модель ≈1 МБ і WebGL на головній → замінюємо на статичні зображення (бриф), модель лишається лише як джерело рендерів.
6. Обмеження localStorage (~5 МБ): журнал телеметрії має бути стиснений і обмежений (напр. 1 точка/хв, 30 днів).

## 4. Архітектура 4.0 (без переписування протоколів)

```
Протоколи (без змін): Fossibot · Bluetti · EcoFlow · Tesla · svitlo.live
          │ адаптери (тонкі, нові)
          ▼
     Tel — сховище телеметрії: station{pct,inW,outW,tf,te,t}, grid{on,V,Hz,W}, gen{on,W}, car{pct,kW,st,t}
          │ підписка (≤ 1 перемалювання на кадр)
          ▼
 UI 4.0: Огляд · Пристрої · Аналітика · Система   (старі екрани лишаються, поки нові не перевірені)
```

- Адаптери читають `BT/BLUP/EF/TS` після кожного кадру даних і пишуть у `Tel`. UI більше не читає протокольні об'єкти напряму.
- `Tel.fresh()` вирішує «живі дані / останній відомий стан / Немає даних» (15 с для станції, 2 хв для авто).
- Журнал для Аналітики пишеться з `Tel`, а не з протоколів.

## 5. Живий потік енергії — технічне рішення

- SVG: для кожного зв'язку базова лінія + лінія-імпульс (`stroke-dasharray`) + м'яке світіння.
- Рух: одна нескінченна Web Animation на лінію (`strokeDashoffset`). Швидкість і напрям змінюються через `updatePlaybackRate()` з плавним переходом 0,7 с — без перезапуску і стрибків; від'ємна швидкість = зворотний напрям.
- Швидкість ∝ log(потужності); товщина/світіння ∝ потужності; при 0 Вт лінія плавно гасне до спокійного стану.
- Колір = роль: мережа (блакитний), генерація (бурштиновий), споживання (світлий), зарядка авто (акцент).
- Лінія світиться лише коли `Tel` підтверджує потік і дані свіжі; застарілі дані → лінія сіра, підпис «немає даних».
- Пауза анімацій, коли застосунок у фоні; `prefers-reduced-motion` і перемикач «Анімація» → статичний стан.

## 7. Наступні кроки (після затвердження)

1. Модуль `Tel` + адаптери Fossibot/Bluetti/EcoFlow/Tesla/svitlo у робочому застосунку.
2. Новий «Огляд» як перша вкладка; старі вкладки доступні з «Пристрої» і «Система».
3. Журнал телеметрії → «Аналітика» (споживання/заряд/розряд за доба/тиждень/місяць).
4. Зображення обладнання — після того, як будуть файли з правом використання.
5. Перевірка на телефоні: плавність, тривала робота, Bluetooth, оновлення зі збереженням даних.
